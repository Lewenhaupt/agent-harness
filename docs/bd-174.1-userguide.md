# Fleet publish mode and the `fleet.json` v2 intent (bd-174.1)

Before bd-174.1 a fleet recorded *where it ran* but never *what should happen to
the merged work*. `fleet.json` had an optional `baseBranch`, and every reader
that needed it carried its own `?? "main"` fallback, so "the fleet lands on main"
was an assumption in seven places rather than a fact on disk. There was no way to
say "this repository publishes its fleet work as PRs" at all.

bd-174.1 makes the landing contract an explicit, frozen part of the intent:

- `FLEET_SCHEMA_VERSION` is now **2**, and a v2 `fleet.json` carries two required
  fields — `baseBranch` (the branch the fleet lands on) and `publish` (a
  discriminated union on `mode`: `local`, `pr`, `push`);
- `publish` is resolved **once per launch** from `--publish*` flags → repo config
  → git config → the inert `local` default, and then frozen into the record;
- a v1 record is migrated on read, so nothing needs hand-editing.

> **This bead publishes nothing.** `local` resolves no remote and runs no
> command. `pr`/`push` only *record* what the fleet was launched to do: the
> `git push` and `gh stack link` steps are bd-174.3 and the pure `gh` core is
> bd-174.2. After upgrading, a `pr` fleet still merges locally — the contract is
> there for the next milestone to read, not to act on.

| Piece | Where |
| --- | --- |
| Mode/field schema, resolver, config reader, `formatFleetPublish` | `src/fleet-publish.ts` |
| `FLEET_SCHEMA_VERSION = 2`, v2 `baseBranch`/`publish` fields, `migrateFleetIntentV1`, `fleetIntentWriteRefusal` | `src/fleet-status.ts` |
| `createFleetIntent` / `writeFleetIntent` and the v1→v2 write migration | `src/fleet-state.ts` |
| Freeze on every later write (`inheritFleetFacts`), `mergeFleetIntent` | `src/fleet-launch.ts` |
| `--publish*` / `--no-publish-ready` parsing, usage text | `src/fleet-launch.ts` `parseFleetCommandArgs` |
| Launch wiring (`resolveLaunchPublish`, resolve-before-side-effect) | `extensions/capabilities/fleet.ts` `runFleetLaunch` |

## What changed / who this affects

**If you run fleets.** Nothing you type has to change: a bare `/fleet bd-12` still
stops at `local`, which is exactly the old behaviour, and the record now says so
instead of leaving readers to guess. The new flags are `--publish
<local|pr|push>`, `--publish-remote`, `--publish-base`, `--publish-ready` /
`--no-publish-ready`, `--publish-stacks <per-chain>`; the tool accepts
`publish`, `publishRemote`, `publishBase`, `publishReady`, `publishStacks`.

**If you read `fleet.json`.** `baseBranch` is required and concrete, and `publish`
is always present. A v1 file reads fine (migrated on read to
`baseBranch: "main"`, `publish: { "mode": "local" }`); anything that is neither v1
nor v2 (`schemaVersion: 99`, truncated JSON) is still `corrupt-intent` and is
never "repaired". `writeFleetIntent` always writes v2 bytes.

**If you supervise.** The contract is frozen at the first launch and preserved by
every later write — re-arm, `belayd_fleet_advance`, pause/resume, reconcile, park
repair, release. Editing `.belayd/config.json` mid-run cannot move where a running
fleet lands; only a new fleet (a new `fleetId`, or a record that was removed)
resolves a new contract.

Two rules worth reading once, because they are deliberate and not obvious:

1. **An explicitly requested bad value is a refusal; an ambient one is a warning.**
   A value that arrives on a flag or a tool parameter (`--publish local
   --publish-remote fork`, `publishBase: "a\nb"`) stops the launch before any side
   effect: a value an operator typed must never be silently discarded. A bad value
   found in `.belayd/config.json` or `git config` is reported (one warning per
   problem) and ignored, because a stale repo config must not block a launch.
2. **The stored schema is more permissive than the resolver, on purpose.** A
   hand-planted `{"mode":"local","remote":"x"}` in `fleet.json` parses as valid
   `{"mode":"local"}` — the zod object is not strict about an inapplicable
   companion key, so a record written by a *future* mode is not rejected by an
   older reader. The resolver refuses that same combination at launch, because
   there the operator is asking for something the mode cannot carry. Stored data
   must be forward-compatible; operator input must be precise.

and `the config declares "…"` when the source's *own* declared mode cannot carry a
field it also carries (`{"mode":"local","remote":"x"}` in a config file is exactly
this: the reader accepts it, the resolver refuses it).

## How to Use

### Keep the default (nothing to do)

`local` is inert: no remote is resolved, no publisher is spawned, no network is
touched. A bare `/fleet bd-12 bd-15` (or `belayd_fleet_launch { tasks: [...] }`)
freezes:

```json
{ "schemaVersion": 2, "baseBranch": "main", "publish": { "mode": "local" } }
```

into `<git-common-dir>/belayd/fleet/<id>/fleet.json` alongside the fields it always
had. `baseBranch` is the branch you launched from (frozen at launch; `main` if the
branch could not be read), and it is now the single source of truth — the fleet's
merge preconditions read it instead of assuming `main`.

### Turn publishing on for a repository

`<repo-root>/.belayd/config.json`, either shape:

```json
{ "publish": "pr" }
```

```json
{ "publish": { "mode": "pr", "remote": "origin", "base": "main", "ready": true, "stacks": "per-chain" } }
```

`pr` is completed from the launch's `baseBranch` and `origin` when you leave
`base`/`remote` out, so `{"publish": "pr"}` is a complete, valid policy. The file
is **repo-scoped**: it is read from the main checkout (the parent of the shared
`git-common-dir`), so every linked worktree sees the same contract and a
worktree-local `.belayd/config.json` is deliberately ignored. In this repository
`.belayd/` is gitignored, so the file is per-checkout — pass `--publish pr` on a
fresh clone, or use `git config` below and set it again there.

Per-key git config, same repository:

```bash
git config belayd.publish pr
git config belayd.publish.remote origin
git config belayd.publish.base main
git config belayd.publish.ready true
git config belayd.publish.stacks per-chain
```

### Override it for one fleet

Precedence is per field, first source that supplies it wins: flag/tool parameter →
`<repo-root>/.belayd/config.json` → `git config belayd.publish*` → `local`.

```text
/fleet bd-12 bd-15 --publish pr --publish-remote origin --publish-base develop \
      --publish-ready --publish-stacks per-chain
```

```json
{
  "tasks": ["bd-12", "bd-15"],
  "publish": "pr",
  "publishRemote": "origin",
  "publishBase": "develop",
  "publishReady": true,
  "publishStacks": "per-chain"
}
```

`--no-publish-ready` (or `"publishReady": false`) states `ready: false` explicitly.
The precedence is per field, not per object: a flag that names only the mode leaves
`remote`/`base` to the config file rather than resetting them.

### Why a mid-run config edit is ignored

The contract is resolved exactly once, in `runFleetLaunch`, **before** any
worktree, intent write, or arm, and then frozen. Editing `.belayd/config.json`
after the launch changes nothing for that fleet: a re-arm, an advance, a
pause/resume, a reconcile, a park repair, and a failed-member prune all preserve
the recorded `baseBranch`/`publish`. To change where a *running* fleet lands you
would have to edit `fleet.json` by hand, which no documented path supports.

### What upgrading does to existing fleets

A v1 `fleet.json` needs no action: it is migrated on read (`baseBranch` keeps any
recorded value or becomes `main`; `publish` becomes `{"mode":"local"}`) and the
next write stores v2 bytes. But a fleet that is **already running** keeps the
`local` contract it just migrated to — it will not pick up the `pr` you add to
`.belayd/config.json`. A repository that wants `pr` must launch a new fleet (or a
different `--fleet <id>`) so the mode is resolved and frozen for it.

### Failure modes

| Situation | What happens | What you see / do |
| --- | --- | --- |
| `--publish local --publish-remote fork`, `--publish push --publish-base x`, `--publish-stacks` on a `push`/`local` contract | Launch refused before any worktree, intent write, supervisor arm, or audit line | `publish: "remote" only applies to mode "pr"/"push", but mode resolved to "local". Drop the flag or set a mode that uses it.` |
| A config object whose own mode cannot carry a field it carries (`{"mode":"local","remote":"x"}`) | Refused, naming the *declared* mode | `publish: "remote" only applies to mode "pr"/"push", but the config declares "local". Remove the field or change the mode.` |
| A flag/tool value that starts with `-` or contains a control character | Refused (never frozen — a later process executes these strings) | `invalid publish contract (remote: must not start with '-')` / `(base: must not contain control characters)` |
| Unreadable or invalid `.belayd/config.json` (bad JSON, non-object root, unknown `publish` string, wrong type, invalid field value) | Warned once and dropped; the launch proceeds on the remaining sources and never silently upgrades the mode | `<path>/.belayd/config.json: unknown publish "deploy"; ignoring` |
| An invalid `git config belayd.publish*` value | That **key only** is dropped, with a warning; the rest of the git-config source survives | `git config belayd.publish.ready: not a boolean ("maybe")` |
| `belayd.publish` is invalid while `belayd.publish.base`/`.remote` are valid | The mode drops to `local`, so the surviving field has no mode that can carry it → the launch is refused | Same refusal as the first row. Unset or fix the companion key: `git config --unset belayd.publish.base` |
| git itself is unusable (no `git`, `GIT_DIR` outside a checkout, timeout) | One warning per `belayd.publish*` key; the source is treated as unset rather than as "the operator set nothing" | `git config belayd.publish: <error>; treating it as unset` |
| `schemaVersion: 99`, truncated JSON | Read as corrupt; never migrated, never repaired, and a write refuses to replace it | `corrupt-intent` in status; restore the file or remove the fleet directory |
| A v1 record that violated a v1 rule | Still refused during migration — a legacy record is not "repaired" into validity | `parseFleetIntent` → `undefined` |

### Reading the contract back

`formatFleetPublish` gives the one-line form used by launch reports and audit
details: `local`, `pr → origin/develop`, `push → upstream`. The record itself is
read as-is; nothing in bd-174.1 acts on it.

```bash
jq -c '{baseBranch, publish}' "$(git rev-parse --path-format=absolute --git-common-dir)/belayd/fleet/default/fleet.json"
```
